# 0115 — Release 0.5.0: the launch version, its install line and a stability statement

- **Status:** ready (after 0114)
- **Decision:** none (packaging, as task 0080).  Agreed with the user on
  2026-11-08 ("Yes, I want that": a fixed release for the launch post,
  the one-line install, and a stability statement for 0.x).
- **Depends on:** 0113, 0114.  Last before the launch post.

Ground rules for all tasks: [README](README.md#ground-rules).

**Why.**  The launch post should link to a fixed release, so readers see
what was announced while main moves on.  Version 0.4.0 was never tagged,
the CHANGELOG's *Unreleased* section is long, and the README installs
only "from a checkout" (hexmesh isn't on PyPI).  First-time readers also
need to know what a 0.x version promises.

**Where.**  `pyproject.toml`, `hexmesh/version` (wherever `__version__`
comes from), `CITATION.cff`, `CHANGELOG.md`, `README.md` (badge, Install),
`docs/GUIDE.md` if it states a version, `tests/test_readme.py`;
`docs/tasks/` for the tag commands.

**Do.**
1. **The version:** 0.5.0, in `pyproject.toml`, `__version__`,
   `CITATION.cff` (`version`, `date-released`) and the README badge.  A
   test checks they agree (test_readme already checks CITATION's).
2. **CHANGELOG:** *Unreleased* becomes `## 0.5.0 (<date>)`, with a short
   summary at its top (three to five lines: the agent tools, PCF, the
   validation suite, the Python 3.11 floor as **Breaking**), and an empty
   *Unreleased* above it.  Keep the entries as written.
3. **Install:** the README's Install block gains, first,
   `pip install "hexmesh @ git+https://github.com/sigveka/hexmesh@v0.5.0"`.
   Keep `pip install -e .` for a checkout and the "not on PyPI yet" line.
   **Check it** in a clean venv against the pushed tag before the
   release is announced (step 6), and record the result here.
4. **Stability statement.**  A short "Stability" subsection after
   Install, in this sense (wording may be tightened, not changed):
   - hexmesh is at 0.x: the Python API and the CLI's JSON may still
     change between minor versions; every breaking change is marked
     **Breaking** in the CHANGELOG, with what to do.
   - **Saved descriptions** (`Assembly.save`, `to_dict`) carry a format
     version.  Older ones keep loading, migrated on load (as version 1's
     radians are today), or fail with `description_version_unsupported`,
     naming the version.  They are never misread.
   - **Error codes** are stable: a code may be added, and a removed or
     renamed one is a breaking change.
   - Meshes from the same description and version are reproducible
     (byte-identical on the gallery); a change that moves nodes is noted
     in the CHANGELOG.

   Check each promise against the code before writing it: say under
   *Questions for design* if one doesn't hold today (e.g. a code removed
   since 0.4.0 without a **Breaking** line).
5. **A test for the description promise:** a version-1 description (a
   small fixture, written by hand to the old format) loads and builds the
   same assembly as its version-2 equivalent; a made-up version 99 fails
   with `description_version_unsupported`.  Reuse the existing fixtures in
   `tests/data/` where they fit.
6. **The tag and the GitHub release: prepared, not pushed.**  Write the
   exact commands under *Agent notes* (`git tag -a v0.5.0 -m …`,
   `git push origin v0.5.0`, `gh release create v0.5.0 --notes-file …`
   with the CHANGELOG section as notes).  **The user runs or approves
   them**; a release is permanent.  After the tag is pushed, run step 3's
   check and record it.

**Accept.**
- The version agrees everywhere (a test).
- The stability section is in the README, every promise checked.
- The description-version test passes.
- The install line works from the pushed tag in a clean venv (recorded).
- CI green on the release commit; full suite: no new failures.

**Out of scope.**  PyPI (the user's decision; task 0080's follow-up),
and a docs site.
