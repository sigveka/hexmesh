also writes down the steps, so the next release follows a list.

**Do.**
1. **`docs/RELEASING.md`, the checklist,** written from task 0115 and
   this task:
   - **CI green** on the release commit;
   - **the version** in `pyproject.toml`, `__version__`, `CITATION.cff`
     (`version`, `date-released`), the README badge and its install
     line (a test checks they agree);
   - **the CHANGELOG:** *Unreleased* becomes `## X.Y.0 (date)` with a
     short summary on top, and a new empty *Unreleased*;
   - **the cheap validation run:** the quick checks
     (`python3 -m pytest -m openfoam tests/test_validation.py`, needs
     native OpenFOAM) with their pass/fail recorded in the release task.
     Which cases count as cheap: the ones that suite runs (decision
     0050's answer: validation is run for releases, at least the cheap
     cases);
   - **the gallery** regenerated, if meshes changed (`build.py`);
   - **the tag and GitHub release:** the exact commands.  The user
     approves before they run; a release is permanent;
   - **after the tag:** the install line checked in a clean venv.
2. **Follow it for 0.6.0:**
   - **version:** 0.6.0;
   - **CHANGELOG summary:** junction completeness; the snap tolerance
     per reader; `n_outer = 8`; units and scale; the docs.  Mark every
     **Breaking** entry since 0.5.0, and check there is one wherever an
     error code or public name changed.
3. **Record** the quick checks' results and the install check under
   *Outcome*.

**Accept.**
- `docs/RELEASING.md` exists and is linked from CONTRIBUTING.
- The version agrees everywhere (tests).
- The quick checks pass, or each miss is reported.
- The tag and release are made after the user's OK, and the install
  line works from the tag.

**Out of scope.**  Wheels on the release (task 0149, for 0.8); PyPI.
